# Blendit Android Companion — Architecture

## Product goal

A phone-first Android app for requesting, tracking, previewing, and organizing 3D assets generated by Blender. The phone UI should work without requiring Blender to run on the handset.

## Recommended architecture

1. **Android client (Flutter)**
   - Arabic-first, right-to-left interface with optional English.
   - Asset categories: game props, environments, characters, materials, and cinematic scenes.
   - Presets for visual style, detail level, target engine, and output format.
   - Job progress, cancellation where supported, preview gallery, and export history.
   - Download/share generated files and copy the asset manifest.

2. **Generation service**
   - A separate authenticated API receives a validated generation request.
   - A worker runs Blender in background mode with the scripts from this repository.
   - Each job writes outputs to an isolated directory and validates them before being marked complete.
   - Store job status and output metadata; provide expiring download links.
   - Apply quotas, input validation, timeouts, and cleanup to avoid unbounded compute costs.

3. **Blender worker**
   - Reuse generators under tools/blender/.
   - Keep .blend as editable source and export GLB for real-time engines.
   - Return PNG previews and a JSON manifest.
   - Never accept arbitrary Python code from an unauthenticated phone client.

4. **Storage and delivery**
   - Store generated binary assets in object storage or a suitable artifact store.
   - Do not use GitHub Actions as the permanent interactive API or production job queue; Actions remains useful for CI, smoke tests, and scheduled batch generation.
   - Keep large generated outputs out of normal Git commits.

## Suggested first release (MVP)

- Home screen with asset categories and recent jobs.
- Create request form: asset type, prompt/description, style preset, detail level, output format.
- Job status screen: queued, running, validating, ready, failed.
- Preview screen and download buttons for GLB, BLEND, PNG, and manifest where available.
- A sample/demo mode that displays the committed starter pack even before a generation server is configured.

## Implementation sequence

1. Finish and inspect the current Blender generation workflow.
2. Define a versioned request/response schema and job status model.
3. Build the Flutter Android UI against a mock API and demo assets.
4. Implement an authenticated API and isolated Blender worker.
5. Connect the app to the service and test download/preview on Android.
6. Add release signing, crash handling, security limits, and cost monitoring.

## Important constraints

- Full Blender should not be assumed to run natively inside the Android app.
- A server or user-owned computer needs to perform the Blender generation work.
- A cloud service can incur compute and storage costs.
- The first milestone is a usable client and a verified generation pipeline, not a claim that the entire product is already deployable.
